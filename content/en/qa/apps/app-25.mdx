**Starting from the macOS (Tahoe) generation, Apple officially extends Declarative Device Management (DDM) to support non-App Store enterprise `.pkg` software installations. This provides a more modernized, low-latency, and highly transparent deployment experience compared to the traditional Jamf Policy architecture.**

## DDM Package vs. Jamf Policy

| Feature               | Jamf Policy (Legacy Architecture)                                                                  | DDM Package Declaration (Modern Architecture)                                                                                               |
| :-------------------- | :------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------ |
| **Execution Core**    | Heavily relies on the `Jamf` binary agent to execute scripts and run installers in the background. | Relies directly on the macOS native MDM framework to execute the installation.                                                              |
| **Trigger Mechanism** | Requires a defined trigger (e.g., Login, Recurring Check-in).                                      | **Autonomous Evaluation**. The system attempts installation instantly as soon as the device determines it meets the declaration conditions. |
| **Status Reporting**  | Reported via Jamf Pro logs, subject to polling delays.                                             | **Real-time Reporting**. Installation progress and error codes are pushed immediately to the MDM status channel.                            |
| **Offline Support**   | The device must be connected to the Jamf Pro server at the exact moment the policy is triggered.   | Once the device receives the Declaration, it can manage the installation process and retries offline in the background.                     |
| **Suitability**       | Any custom installer or script format (.pkg, .dmg, .sh).                                           | Strictly limited to standard **Distribution Packages (.pkg)** signed by Apple.                                                              |

## Requirements & Limitations

- **OS**: macOS 26 (Tahoe) or later.
- **Package Quality**:
  - Must be a **Distribution Package** (not a basic component pkg).
  - Must be **signed** with a valid Apple Developer ID Installer certificate.
  - Must be **notarized** by Apple. MDM deployment in macOS 26 is extremely strict regarding security; unsigned or un-notarized packages will fail with a `VerificationFailed` error in the status channel.

## When to use each?

- **Use DDM Packages**: For deploying standard, large-scale software architectures (e.g., Microsoft Office, Google Chrome, Adobe Acrobat), or when you need real-time visibility into the "installation success rate" for critical apps on modern macOS environments, minimizing reliance on the Jamf binary.
- **Maintain Jamf Policies**: For highly complex deployment workflows (e.g., requiring a Bash script to modify `.plist` preferences post-installation, or requiring interactive prompts), non-standard `.pkg` formats (like drag-and-drop `.dmg` apps), or legacy macOS devices.

## Expert Tip: The Notarization Check

Before uploading a .pkg to Jamf for DDM deployment, run the following command on your admin Mac to ensure it will be accepted by macOS 26:

`pkgutil --check-signature path/to/your.pkg`

If the signature chain is not valid all the way to the Apple Root CA, the DDM deployment will be rejected by the client device's security framework.
